This document records source inspection and the proposed implementation order. It is not runtime acceptance evidence. Issue #91 remains open.

The focused `test:worker-trust-security` gate runs the trust-store, signed-pairing, authentication, server-contract, security-audit, and audited-trust-administration suites. The Electron/TypeScript workflow invokes it as a required step on both Ubuntu and Windows x64 matrix jobs. This wires the checks into CI; exact-head CI results and Windows service/DPAPI/ACL acceptance are still pending and are required before issue closure.

The live named-pipe path now reads and bounds the client header before impersonation, retains the first-instance server handle between requests, and the provisioner verifies the connected server PID and executable against the installed SCM service before sending signed bytes. Running-service trust updates automatically use the live pipe; startup credential bootstrap remains on the protected staging path. The worker control loop now reuses one stream iterator across transactions. Regression checks cover these source contracts and repeated-frame listener cleanup. These checks do not replace a Windows SCM/pipe runtime test.

## Closure evidence

This branch is not yet accepted or merged. Closure requires the implementing PR into `dev`, human review, required exact-head CI, and linked Windows runtime evidence. The installed worker and its children must be nonadministrator; listener scope must match loopback/private adapter; disconnect must not stop a bounded campaign; rotation/revocation must deny the old identity on fresh connections; cross-controller access must not read or stop another run; and shutdown/restart must preserve truthful journal state. Pure logic tests and the direct-coordinator acceptance from #90 do not substitute for installed-service behavior.

The audit checkpoint protects against log rollback while the latest protected checkpoint remains intact; it does not protect against restoring a complete older snapshot of the key, checkpoint, and all segments. That boundary is an explicit limitation, not whole-directory rollback protection. The directory must be writable only by the dedicated service identity and must have one live writer. Windows acceptance must validate ACLs and singleton service startup before treating the log as a production audit trail. If whole-snapshot rollback protection is required, add and review a monotonic external anchor before claiming it.

## Fuzz-child write and read boundary

The verified native launch creates WinAFL with a restricted primary token. `DISABLE_MAX_PRIVILEGE` removes service privileges other than Windows traverse privilege, and the token applies a full restricting-SID check using the per-run SID, `S-1-5-12` Restricted Code, `S-1-5-11` Authenticated Users, and World. Authenticated Users is present only in the restricting-SID list; it is not added to the token's default object DACL. New named objects remain accessible only to the worker identity and that run's random SID, so another run cannot open them. The ordinary worker-token check still applies in addition to that restricted-SID check. Elevated provisioning grants Restricted Code read/execute on the installed tool/runtime tree, read and traversal on input directories, and read only on input files; ACLs are applied per object so directory traversal cannot inherit execute rights onto PDFs. The output root receives traversal only. It does not grant Restricted Code access to trust, audit, SQLite, or DPAPI credential paths. A fresh random SID receives modify rights only on that run's empty evidence directory; sibling runs do not receive that SID.

**Confirmed and corrected containment failure:** the exact-head Windows standard-user probe on `78c1e2d5cf247748ead2f811e5839357e0e2c164` wrote to a World-writable sentinel outside run evidence (probe exit `49`). The Authenticated Users fixture and run-private event checks were not reached on that head. The launch token's restricting list now contains only the per-run random SID and Restricted Code; the broad World and Authenticated Users SIDs have been removed. This is a source-level correction only. Keep the acceptance item open until exact-head Windows tests prove both broad-ACL writes are denied and WinAFL's namespace access works with the reduced restricting list.

Child-created named kernel objects use a private default DACL for the worker identity and that per-run SID, so WinAFL/DynamoRIO descendants can share run-local IPC without making the objects world-accessible. The native Windows supervisor contract probe must prove that a child and its descendant can write evidence and use a named event while both are denied reading and writing a protected sentinel. Exact-head Windows execution of this probe and a genuine WinAFL/DynamoRIO campaign remains required before this boundary is accepted. See Microsoft’s [restricted-token model](https://learn.microsoft.com/windows/win32/secauthz/restricted-tokens) and [`CreateRestrictedToken`](https://learn.microsoft.com/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken).
