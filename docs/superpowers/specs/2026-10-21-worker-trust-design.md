# Worker trust and Windows service — issue #91

Status: approved by the user on 21 October 2026, including the trust model, default-deny API/audit policy, native SCM boundary, and all three implementation plans. Implementation and Windows acceptance remain in progress.

## Intent and scope

Complete issue #91 on the Electron/TypeScript architecture: a Windows x64 worker runs independently of the desktop, under a dedicated nonadministrator identity, and exposes an authenticated API only on loopback or an explicitly selected private/VPN adapter. Every request is authorized against current trust and resource ownership. Certificate lifecycle, bounded admission, safe audit records, and installed-service acceptance are part of this work.

The baseline is `501102a6abf0e4aec0a3efefabb7904413d0fa9a`. The source audit is `docs/security/worker-trust-acceptance.md`. Existing signed pairing bundles, organization signing public key, worker/controller UUIDs, one active campaign, authoritative run journal, and genuine native gates remain the integration contracts. No new runtime package or third-party service wrapper is needed.

## Trust-boundary review against the current source

I reviewed the API, desktop pairing flow, worker coordinator, input-bundle path, artifact access, and existing TLS tests at the baseline above. This is a source review, not proof of installed Windows behavior or a penetration test.

- **Observed — the desktop verifies the signed bundle, but the worker does not yet provision trust from it.** `apps/desktop/src/main/worker-bundle.ts` verifies the organization signature and the desktop checks the signed worker/controller UUIDs against the TLS-authenticated capabilities response. `apps/worker-service/src/server.ts` currently receives a startup `pairedControllers` map. Therefore the operator-side worker provisioning command must independently verify the bundle with the worker's configured organization public key, then derive the active mapping from the controller certificate in that verified bundle. It must never accept a controller UUID or fingerprint supplied separately by an unauthenticated CLI argument or renderer.
- **Observed — request identity is derived from the peer-certificate fingerprint, and request-body identity is only a consistency check.** The server passes the mapped controller ID into handlers; `validateStartRequest` rejects a mismatching `controller_id`. Custom identity headers do not grant authority. The persistent trust record must preserve this property and map one active certificate fingerprint to exactly one controller UUID.
- **Observed — run ownership is checked before dispatch on each run subresource, and again in the coordinator.** The API checks the run-store owner before status, stop, event, manifest, or artifact handlers; coordinator methods repeat ownership checks. Input bundles are placed under the authenticated controller's directory and run verification is rooted beneath that controller directory. Keep both boundary checks; a route matrix and two-controller tests must make omissions visible.
- **Observed — certificate validation is split across TLS and a small application check.** `requestCert` and `rejectUnauthorized` require a CA-authorized peer; `auth.ts` adds fingerprint syntax, validity-window, paired and revoked-set checks. The application does not currently inspect X.509 CA/basic constraints, key usage, EKU, key algorithm/strength, or a persistent revocation source. TLS chain validation must not be mistaken for the complete application certificate policy. Before trusting a provisioning bundle, parse its certificates and explicitly enforce leaf purpose and key policy; test each rejected property with real TLS fixtures. Bind the signed worker pin to the exact worker certificate and bind the controller fingerprint to the signed controller UUID.
- **Observed — revocation is not live today.** Paired and revoked sets are copied into `createWorkerServer` at startup. Although the request callback checks them on every request, it checks immutable snapshots; an operator change cannot revoke an existing keep-alive/TLS connection. Resolve active trust state for every request from a bounded authoritative repository, commit revocation before reporting success, and close sockets for the revoked fingerprint. An already authorized bounded operation may finish only under the explicit bounded-operation policy.
- **Observed — run-resource denials share a not-found response, and unexpected errors are generic.** Keep this anti-enumeration behavior while assigning stable safe error codes and request IDs. Authorize before archive extraction, run launch, event reads, or artifact I/O. Audit unauthenticated TLS failures separately at a bounded connection-level rate; they may not have a trustworthy controller identity or HTTP request ID.
- **Inferred — the organization signing key and local administrator are high-impact roots.** A signing-key compromise can mint trusted pairing bundles; a local Administrator can replace service files or inspect its process. This design narrows routine service and desktop authority but cannot defend against compromise of the organization root, Windows kernel, or a fully privileged local administrator. Keep the signing private key out of this repository and build, document root rotation/recovery as an operational ceremony, and state this threat-model boundary explicitly.

These findings require a persistent lookup per request, worker-side signature verification during provisioning, explicit X.509 purpose/strength checks, and tests for rotation/revocation on reused connections. They do not invalidate the selected certificate-fingerprint-to-controller identity model; they make trust transitions concrete and fail closed where the current implementation still relies on startup configuration.

## 1. Components and service identity

Add a small Windows SCM executable under `native/worker-supervisor`. It registers service status/control handlers, launches only the fixed installed Node executable and TypeScript worker entrypoint, and carries bounded readiness and shutdown messages over inherited local pipes. It does not interpret network input, select fuzzing tools, or own campaign policy. All application, trust, HTTP, and recovery behavior remains TypeScript.

An administrator performs one-time installation under `NT SERVICE\SumatraFuzzWorker`, enables the dedicated service SID, and installs protected configuration and executable paths. Administrators can change deployment policy; the service can read its runtime/tool roots and modify only designated data, security-state, and evidence directories. Ordinary desktop users cannot replace executable code, keys, trust configuration, or service controls. The native host rejects elevated/SYSTEM worker execution and inherited executable/environment overrides, including Node preload options. Arguments use the existing Windows argument encoder and fixed executable paths.

The provisioner verifies a dedicated NTFS worker-data volume and an enforced service-identity quota matching the worker disk policy. Runtime verifies the identity, roots, quota, and ACL conditions before opening a listener. Installation rollback removes only resources created by this installation. Uninstall drains/stops the service and removes its named firewall/service configuration; it retains evidence and security state unless the operator separately requests data deletion.

The SCM host owns an outer kill-on-close Job Object for the Node process and descendants. Existing per-campaign jobs remain nested inside it. Normal service stop denies new work, drains bounded HTTP work, requests coordinator teardown/finalization, closes journal handles, and then reports stopped. The host allows up to 60 seconds before terminating its child tree; a forced termination never invents a successful teardown receipt or Completed state. Startup uses existing conservative reconciliation and never silently relaunches a campaign. Desktop exit and network loss do not send service-stop commands.

## 2. Listener and transport

Local mode binds only to its explicit loopback IP. Remote mode requires an exact private/VPN IP, stable Windows adapter identity, port, and allowed peer CIDRs in administrator-controlled configuration. Startup verifies that address belongs to that adapter. No wildcard, hostname, public fallback, discovery, or enrollment listener is added.

The provisioner installs a named firewall rule scoped to the installed program, local address, selected adapter, configured peer CIDRs, and Domain/Private profiles. It verifies the effective policy and rejects configurations whose intended restriction cannot be established; it does not rewrite unrelated firewall rules. Adapter/address loss closes admissions and the listener. An active campaign continues within its resource limits; recovery of networking requires explicit service restart after configuration is verified.

Server and controller client require TLS 1.3. There is no TLS 1.2 exception in this design. Chain validation, expiry, expected certificate purpose, key strength, worker hostname/IP SAN, SHA-256 pin, and signed worker/controller UUID checks all apply. Accept explicitly supported RSA keys of at least 2048 bits or P-256/P-384 ECDSA certificates; provision RSA-3072 by default. Reject CA certificates as endpoint identities, missing/wrong EKU, invalid validity periods, and unsupported or weak certificate algorithms. The worker provisioning command independently verifies the signed bundle before activating its controller fingerprint-to-UUID mapping. The organization Ed25519 bundle-signing key is a separate trust purpose; its private key is an offline organizational secret, never a repository/build input. Document a deliberate root-rotation and compromise-recovery ceremony; a compromised root or local Administrator is outside the protection this worker service can provide.

## 3. Persistent trust and certificate lifecycle

Add a versioned security database separate from the authoritative campaign database. Its trust records bind certificate fingerprint, controller UUID, permissions, validity window, status, and revision. Every authenticated request resolves its principal from this store; JSON fields and custom identity headers cannot grant identity or permissions. All existing routes use an explicit deny-default policy matrix, followed by run/artifact ownership checks. Unknown and cross-controller resources return the same safe 404 shape.

Trust administration is an operator-only local workflow protected by service/admin ACLs, not a network API. Provision, renew, rotate, revoke, and unpair are explicit audited operations. Rotation installs the replacement fingerprint for the same controller with a bounded overlap and explicit expiry of the old record. Revocation commits before success is returned, denies subsequent requests on existing keep-alive/TLS sessions, destroys affected sockets, and clears their admission state. An already authorized bounded operation may finish; a new request must reauthorize. Revocation does not implicitly stop a running campaign; an administrator can stop the service when containment is required.

Worker credentials are imported through a service-readable, administrator-protected staging file, validated under the service identity, encrypted using current-user DPAPI, and removed from staging before normal listening begins. Import failure leaves the service unavailable and reports a safe operator error. Private keys never enter SQLite, logs, arguments, renderer IPC, result bundles, or CI artifacts. Buffers holding private material are cleared where ownership permits; no guarantee of physical secure erase or complete elimination of runtime key copies is claimed.

Retain the approved signed `.sfpair` controller-import flow and its DPAPI desktop storage. A temporary pairing file contains controller private material and must use protected local permissions and a trusted private transfer channel; it is not an evidence/export bundle. Worker certificate renewal updates protected credentials and requires newly signed pairing material for the new pin. Unpair removes the active desktop profile and revokes its worker trust record through the operator workflow. Organization signing-root rotation continues to require a reviewed desktop build and a documented worker trust-store migration; the worker must not silently fall back to an unknown or unsigned root.

## 4. Admission policy and safe responses

Centralize validated security budgets. The following are candidate thresholds to exercise in tests and benchmarks; they are not measured production capacity. Installed policy is explicit and administrator-owned. Record benchmark results and review chosen installed values before treating them as release defaults; silent relaxation is forbidden.

| Boundary | Candidate limit |
| --- | --- |
| HTTP headers / request target | 16 KiB / 4 KiB |
| JSON body / archive body | 1 MiB / existing 32 MiB maximum |
| Connections / TLS handshake | 64 total sockets / 10-second handshake deadline |
| Active requests | 32 globally, 4 per controller |
| Rate | 10 requests/second, burst 20 per controller |
| Ordinary request / idle / headers | 30 seconds / 30 seconds / existing 15 seconds |
| Upload absolute deadline | 120 seconds, with the same idle deadline |
| Artifact transfers | 2 per controller, 8 MiB maximum response chunk |
| Event replay | 1 request per controller/run, 500 events/page, 64 KiB/event, 4 MiB/page |
| Trust-state cardinality | 16 active controllers, at most 2 nonrevoked certificate generations each |

Keep the existing single archive-import gate and aggregate disk ceiling. Reject unsupported content types and ambiguous framing before reading application bodies. Admission precedes expensive work. Release timers, counters, buffers and socket references on finish, abort, timeout, revocation and shutdown. Bound caches by the configured trust/connection limits; no unbounded per-address or per-UUID map is introduced.

Errors use stable codes and generated correlation IDs, safe status codes, and bounded Retry-After for overload. Responses and logs contain no stack trace, absolute host path, raw input, key, or certificate body. Failure paths must not invoke campaign launch. Existing protocol-required fields remain validated, and client error handling is updated with the same contract.

## 5. Security audit and integrity

The security store retains redacted UTC records for principal fingerprint/controller ID, action, run/artifact identifier when applicable, decision, correlation ID, trust revision and payload digest where useful. Raw request bodies and private paths are excluded. Record trust changes and privileged-operation intent before performing their effect, then record the observed result. Audit failure denies new privileged operations and places the service into an operator-visible degraded state; it does not silently stop or fabricate the state of an already running campaign.

Authenticate ordered audit records with a chained HMAC whose key is DPAPI-protected outside the database. Maintain a separately protected checkpoint of the last durable sequence/hash using atomic replacement. On recovery, a verified extension after an older checkpoint may be accepted and checkpointed; a missing prefix, changed record, or database older than its checkpoint blocks privileged operation. This detects alteration and rollback behind the last checkpoint, not an administrator restoring both stores or loss within a crash window before checkpoint persistence. Retention rotates sealed segments with continuity metadata and an explicit policy bounded by the worker disk quota; exhaustion denies new privileged work and requires operator recovery rather than silently dropping records.

## 6. Test and acceptance evidence

Use focused tests observed failing before implementation, then unit and real TLS integration tests. Cover TLS 1.2 denial on both endpoints; missing, unpaired, expired, revoked, wrong-purpose, CA-as-leaf, weak-key and wrong-anchor certificates; worker-side rejection of unsigned, altered, expired, wrong-UUID or fingerprint-mismatched pairing bundles; wrong worker pin/UUID; spoofed identity headers; two-controller denial for every run/event/manifest/artifact/stop route; revoked reused connections and TLS session resumption; restart of trust state; malformed policy; request/content/size/rate/concurrency/deadline exhaustion; audit modification/checkpoint rollback; and cleanup after aborted connections. Handler spies may verify no dispatch in negative API tests, but cannot satisfy native execution acceptance.

Add a required disposable Windows x64 service job. Only installation/configuration executes elevated; the SCM host, Node worker, and parser descendants must be observed under the nonadministrator service identity. Exercise install/start/stop/restart/uninstall, protected-file denial to ordinary users, loopback/private adapter and firewall refusal, DPAPI wrong-user/tamper denial, network/controller disconnect, quota setup failure and forced service termination. Run the genuine pinned WinAFL/DynamoRIO acceptance through the installed authenticated service, not only the direct coordinator. Upload bounded sanitized metadata, hashes, principal/token assertions and receipts, never fixture private keys or input corpora.
